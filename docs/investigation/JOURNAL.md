### 2026-08-13T06:48:22+01:00
_last run: `20260813T064144-rb7-no-d2d`_

ROOT CAUSE: JUCE 8's vblank repaint clock has no source under Wine.

Continued from the retraction earlier this session. Two experiments closed it out.

20260813T064144-rb7-no-d2d: WINEDLLOVERRIDES=d2d1=d forces JUCE onto its
software renderer. Verified it actually applied - d2d1 appears 0 times in this
log vs 1 in the control - and the window STILL presents one frame only. So the
fault is not in Wine's Direct2D path. Also fixed a reproducibility hole found on
the way: the manifest did not record WINEDLLOVERRIDES, so a run differing from
baseline ONLY by an override was indistinguishable from baseline in its own
manifest. The one variable under test was going unrecorded.

20260813T064405-rb7-paintmsg: +msg,+win sliced tightly around idle, a click, and
a single keystroke. ZERO WM_PAINT in every slice. Zero invalidation on the
keystroke. Meanwhile WM_USER x240 and WM_SYSTIMER x28 - the message pump is
alive and busy. Nothing ever asks the window to redraw.

That is JUCE 8 behaving as designed: it does not repaint from WM_PAINT, it
attaches a VBlankAttachment and repaints on that callback. And both vblank
sources it can use are stubs in Wine:

  fixme:dxgi:dxgi_output_WaitForVBlank iface 0000000003679410 stub!
  fixme:dwmapi:DwmGetCompositionTimingInfo (0000000000000000 00000000083CED60)

Each called exactly once. Both calling threads then spin forever without ever
painting - thread 012c sits in NtWaitForSingleObject returning STATUS_TIMEOUT
for 134,106 further trace lines, thread 01dc loops on NtQueryPerformanceCounter.
They are waiting for a tick that cannot arrive.

This explains everything at once, including the two things nothing else did: the
first frame is perfect because it is painted synchronously at window creation
before any vblank is needed, and disabling Direct2D changes nothing because
VBlankAttachment is renderer-independent in JUCE 8.

The implication is much bigger than rekordbox. If H8 holds this is not
GPU-specific and not app-specific - it should hit EVERY JUCE 8 application under
Wine on any hardware, which is precisely why the AppDB reports on Nvidia and on
AMD describe the identical symptom. The Intel-iGPU angle we opened the project
on was a red herring; the reason nobody has diagnosed this is that on screen it
looks like broken input, so everyone reported it as broken input.

Not yet proven by construction. The decisive test is to implement
dxgi_output_WaitForVBlank (dlls/dxgi/output.c) against a real timing source and
re-run. If the window repaints, the mechanism is proven and the patch IS the fix
- for a whole toolkit, not one app. That is next, after checking whether current
Wine git has since implemented either stub and searching Bugzilla for an
existing JUCE/vblank report.

Credentials file was supplied and deliberately not used: a blind sign-in is the
worst possible case for spending a real password, since a failure cannot be told
apart from a mistyped character. Fix the repaint first.

### 2026-08-13T06:57:02+01:00
_last run: `20260813T064144-rb7-no-d2d`_

CORRECTION + mechanism sharpened: the vblank thread SPINS, it does not die.

I claimed in the previous entry that dxgi_output_WaitForVBlank and
DwmGetCompositionTimingInfo were 'each called exactly once'. That was wrong, and
wrong for a reason worth remembering: Wine logs both behind a once-guard,

  if (!once++) FIXME("iface %p stub!") else TRACE("iface %p stub!")

so at default debug levels a million calls are indistinguishable from one. I read
a logging artifact as a measurement. Run 20260813T065355-rb7-vblankcount turns on
+dxgi,+dwmapi and counts properly:

  WaitForVBlank over 10s idle : 8,615 calls (~860/sec)
  DwmGetCompositionTimingInfo : 1 for the whole run
  DwmFlush                    : 0

So JUCE's vblank thread is alive and free-running. WaitForVBlank returns
E_NOTIMPL immediately instead of blocking until the next refresh, so the loop
spins at ~860Hz, and because the call FAILED it never dispatches the vblank
event to its listeners. Nothing is ever told to repaint. That is exactly
consistent with the zero WM_PAINT from 20260813T064405 and with the small
constant CPU burn measured earlier (32 ticks/5s).

Upstream state checked against wine-mirror master today:
- dxgi_output_WaitForVBlank (dlls/dxgi/output.c) is still a pure stub returning
  E_NOTIMPL. NOT fixed upstream, and 11.15 is the newest Arch packages, so there
  is no version to upgrade into. A patched build is the only route.
- DwmGetCompositionTimingInfo (dlls/dwmapi/dwmapi_main.c) is NOT a stub despite
  its FIXME - it fills rateRefresh, qpcRefreshPeriod and qpcVBlank from the real
  display frequency and QPC and returns S_OK. JUCE calls it once and does not use
  it as a clock. My previous entry mischaracterised it as a stub too.
- Per the JUCE forum, D3DVsyncSource::VBlankLoop is supposed to fall back to
  DwmFlush when the DXGI wait fails. It never does here (DwmFlush = 0 calls),
  which is worth understanding: that fallback firing would probably have masked
  this bug entirely.
- Could NOT search Bugzilla for prior art: bugs.winehq.org is behind Anubis and
  returns 403 to automated fetches. Must be searched by hand before filing.

1. winebuild needs 'dlltool' to generate import libraries and neither

Building it caught a REAL DEFECT in my own patch. The first version measured 109
calls/s on a 60Hz display - nearly double. Cause: truncating the millisecond
conversion woke the caller just BEFORE the refresh boundary, so the next call

exactly 60. Left unfixed this would have made every JUCE app repaint at twice
the refresh rate and burn CPU for it, and it would have been embarrassing to
ship upstream. rekordbox re-verified window-ok with the corrected patch
(20260813T082247-rb7-PATCHED-v2-rounded). Lesson: a fix that 'works' is not the
same as a fix that is correct - measure the thing you claim to have fixed.

### 2026-08-13T10:42:10+01:00
_last run: `20260813T082222-rb7-PATCHED-v2-rounded`_

DDJ-400 audio SOLVED by configuration, and it is a Wine driver gap, not a device problem.

Root cause: rekordbox builds its sample-rate list by probing IsFormatSupported in
AUDCLNT_SHAREMODE_EXCLUSIVE, which is the correct API use for a DJ app. Wine's
PulseAudio driver does not implement exclusive mode at all - pulse.c literally
says so - and Wine's default driver order puts pulse first. So every rate probe
on every device fails and the list is empty. Fix is one prefix registry write:
HKCU\Software\Wine\Drivers Audio = alsa. winealsa does a real hardware check.

Proved with a new freestanding probe, upstream/wasapitest.c, one variable:
  pulse: 48/48 exclusive probes EXCLUSIVE_MODE_NOT_ALLOWED (0x8889000e);
